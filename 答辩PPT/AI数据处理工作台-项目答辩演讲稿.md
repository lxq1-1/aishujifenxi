## 第 4 页 · 业务痛点（60 秒）

> 🎤 在做这个项目之前，我先做了**用户访谈**，目标是搞清楚"用 Excel 写汇报的人到底卡在哪里"。

调研结果聚焦在六个高频痛点上：

1. **手工清洗数据**——格式不统一、缺失值、重复行，每次都要用 Excel 公式或筛选，几小时起步；
2. **手动算指标**——合计、均值、同环比、TopN，全靠函数和复制粘贴，公式一变全要重来；
3. **图表靠手动**——插入、选数据、调样式、截图，改一个数字整张图重做一遍；
4. **写报告耗时**——把数字翻译成业务叙述，述职、年度复盘动辄两三天；
5. **格式分发**——老板要 PDF、业务要 Excel、法务要 Word，同一份内容做四遍；
6. **不会写代码**——想用 AI 却不会调 API，想自动化又不会 Python。

> 🎤 这六个痛点的共性是：**重复、低效、易错**。他们不缺数据，缺的是把数据**自动变成可用报告**的工具。

## 第 5 页 · 目标用户（45 秒）

> 🎤 我把目标用户聚焦在三类人身上，他们画像清晰：

- **运营人员**——每周要出活动复盘和渠道分析；
- **销售人员**——每周一/五要把本周的客户跟进数整理一遍；
- **HR 和行政**——年底述职要数据加项目加反思三块结合。

> 🎤 他们的共同特征是：**每周至少花 4 小时在 Excel 上、不写代码、需要向上汇报**。

所以我们产品的核心定位就三个词——**零代码、一站式、中文友好**。用户不需要懂 Python，也不需要懂 Prompt Engineering，只要会上传文件。

## 第 8 页 · 技术栈（60 秒）

> 🎤 技术栈选型遵循两个原则：**生态成熟、能跑在普通服务器上**。

七层技术栈我快速过一遍：

1. **前端**——Vue 3 + Vite + Pinia + Element Plus + ECharts。组件库丰富，ECharts 适合做复杂图表；
2. **后端**——FastAPI + SQLAlchemy + Pydantic。异步高性能、自动生成 OpenAPI 文档，**接口即文档**；
3. **数据处理**——Pandas + openpyxl + pdfplumber + pypdfium2。这一层负责结构化数据处理；
4. **数据库**——SQLite 开发用、生产可换 PostgreSQL；
5. **LLM 接入**——用 OpenAI Python SDK 兼容 **gpt-4o-mini / 通义千问 / DeepSeek**。**OpenAI 协议已成事实标准**，意味着用户可以无成本切换国产大模型；
6. **导出引擎**——reportlab + python-docx + openpyxl + python-pptx，全 Python 实现，**服务器端直出**；
7. **图表渲染**——导出用 matplotlib 生成 PNG，前端保留 ECharts 交互。

> 🎤 所有依赖 24 项，**锁定版本号**，见 requirements.txt。

---

## 第 9 页 · 系统架构（60 秒）

> 🎤 系统是三层架构。**前端薄、后端厚、LLM 仅做文本**——这是本项目最重要的设计原则。

- **前端层**——Vue 3、ECharts、Pinia、Axios，只负责展示；
- **后端层（核心）**——FastAPI 做路由、Pandas Engine 做清洗指标、AI Service 做报告生成、PDF Service 做文档处理；
- **基础设施层**——SQLite 存元数据、文件系统存上传和报告、OpenAI 兼容 API 调模型、导出引擎出多格式。

> 🎤 这里有一个关键的设计哲学——**所有数值计算归 Pandas、文本生成归 LLM、视觉渲染归前端**。这三个角色互不重叠，任何一个挂掉，系统都能降级。

## 第 11 页 · 6 大模块（60 秒）

> 🎤 从数据输入到报告输出，全链路打通。

1. **M1 数据接入**——支持 Excel/CSV 多 sheet 合并上传、预览、重命名、删除；
2. **M2 数据处理**——5 种清洗规则 + 6 种填充策略，30 多个指标自动计算，中文字段自动归一；
3. **M3 AI 分析**——12 套模板，Prompt 模板与业务结构分离，**LLM 失败自动降级到规则**；
4. **M4 辅助工具**——合并、校验、对话、对比、改图、清洗、PDF 处理，**7 个工具覆盖完整链路**；
5. **M5 可视化**——前置生成 8 张以上看板、自然语言改图、3 套风格按需切换；
6. **M6 多格式导出**——16:9 PPT 自动分章节，图表真实嵌入，4 套主题色可选。

> 🎤 每个模块独立可测、可降级、可替换——任何一个环节出问题，系统都不卡死。

## 第 13 页 · 三大难点（120 秒）

> 🎤 这三个问题不是"能不能实现"的问题，而是"实现得**稳不稳**、容错容得**够不够**"的问题。

**【难点一】照片转 PDF · 图片也能变成可搜索文档**

真实办公场景里大量材料不是电子文档——合同是手机拍的，报表是扫描件。它们**没有文本层**，常规 PDF 抽取只能拿到空白；而我们的工作台是"Excel 台账 → AI 报告"，用户拍的照片天然进不来。

我们做了完整的一条链路：

1. **版面 OCR**——用视觉模型拿到 `title` / `role` / `blocks` 的**结构化版面结果**，而不是只出纯文本；
2. **Word 风格重排**——用 `reportlab` 重新排版，文字扶正、正向横排、字号统一；
3. **白底化**——背景估计除法抹平光照不均 + 局部自适应阈值二值化，印章与手写按 bbox **原样贴回**，保住颜色和笔迹；
4. **不可见文字层**——叠一层 `setTextRenderMode(3)` 的文字，成品**既能看原件版式，又能搜索复制**。

最关键的一点是：**任何一环失败都不阻断整批**——单张识别失败只标记该位置，其余照常出 PDF；视觉模型不可用时降级为图片型 PDF，接口不返回 5xx。

效果是：照片、扫描件这类"非结构化输入"，现在也能变成**白底黑字、文字可检索**的正式文档。

**【难点二】LLM 容错 · 让系统在任何情况下都能交付**

API 限流、模型超时、JSON 解析失败、Reasoning 模型把思考链塞进正文——任何一个发生都会让用户看到空白页。

我们的做法是**三层兜底**：

- 第一层，**JSON 模式失败 → 自由模式重试**；
- 第二层，**自由模式失败 → 规则化叙述 fallback**；
- 第三层，**章节漏图 → Pandas 兜底补图**。

另外我们写了 `strip_thinking()` 和 `strip_english_reasoning()`，递归剥离思考链，防止 reasoning 模型污染正文。效果是**AI 不可达时系统仍能交付报告**。

**【难点三】跨模态对比 · 表格 vs PDF vs Word 都能比**

业务上经常出现"两份合同差异"的场景，但合同可能是 Excel、PDF、Word 不同形态。我们设计了 **3 层路由**：

- `contract_compare` 模式 → 12 类条款 × 利弊 × 谈判建议；
- 任一边是非结构化 → LLM 直接读原文做语义对比；
- 双结构化 → Pandas 4 种算子（业务对比、行级变更、分布差异、TopN 排行）。

前端根据文件类型自动切换，后端统一输出 4 键 JSON。

> 🎤 总结这三个难点的共同设计原则——**数据归 Pandas、文本归 LLM、任何环节都可降级**。

# 问答环节 · 预案（建议放最后 2 分钟）

> 下面是常见答辩问题的预设回答，老师问到时可以快速反应。

## Q1: 为什么不用 LangChain / LlamaIndex 这些 AI 框架？

> **A**: 主要考虑两点——**可控性和部署成本**。我们的业务场景是结构化的（清洗、指标、报告模板都有明确 schema），LangChain 的抽象反而增加了调试成本。直连 OpenAI SDK 让我们对每一次 LLM 调用都能精准控制——比如我们能在 prompt_builder 里手动注入指标和模板结构，能在 ai_service 里手动实现三层 fallback，这些都是 LangChain 不容易做的。部署上 LangChain 会带来大量额外依赖，我们追求的是"一个 requirements.txt 就能跑起来"。

## Q2: LLM 调用失败时系统会怎样？用户看到什么？

> **A**: 用户看不到任何空白页。我们做了三层降级：**JSON 模式失败时自动切自由模式重试**；**两次都失败时由 Pandas 算出的指标 + 规则化叙述兜底生成报告**；**如果某个章节 LLM 漏配图表，Pandas 兜底补一张**——保证每个章节都至少有 1 张图。用户看到的可能是内容稍微"机械"一点，但绝不会看到空白。

## Q3: 怎么处理 LLM 输出的不可控？（比如乱编数字、推理模型写思考链）

> **A**: 三个机制：**第一**，所有数字一律从 Pandas 算出的指标里取，Prompt 里**显式禁止 LLM 编造数字**；**第二**，对 Reasoning 模型（DeepSeek-R1 / QwQ / MiniMax-M2.7 等）输出的 `<think>...</think>` 块和正文里的英文推理段，用 `strip_thinking()` + `strip_english_reasoning()` **递归剥离**；**第三**，所有 LLM 输出走 JSON Schema 校验，校验失败就走规则化 fallback。

## Q4: 多用户/并发怎么处理？

> **A**: MVP 阶段是单机部署，所有任务串行处理，每个任务约 30 秒完成。**FastAPI 本身是异步的**，单实例可以处理数十个并发请求；如果业务量上来，**把 SQLite 换成 PostgreSQL、把任务队列换成 Celery + Redis**，SQLAlchemy 抽象层和 Pydantic 接口都不用改。横向扩展上 FastAPI + Uvicorn 支持多 worker。

## Q5: 数据安全/隐私怎么保证？

> **A**: 数据全程留在自己的服务器，不出公网——LLM 调用只把**指标和文本片段**发给模型，**不发送原始 Excel**。生产环境可以把 LLM 切换到本地部署的开源模型（如 Qwen-VL、ChatGLM）实现完全本地化。另外 `.env` 里的 API Key 走 pydantic-settings 读取，不入代码仓库。

## Q6: 这个项目和市面上现成的 BI 工具（如 Tableau、PowerBI）有什么区别？

> **A**: 核心区别是**目标用户不同**。Tableau/PowerBI 是给数据分析师用的，需要学建模、学 DAX；我们做的是**给不会代码的业务人员用的**——他们只要会拖文件，不需要懂 schema、懂公式、懂图表配置。我们的差异化是 **"零代码、中文友好、上传即用"**，并把 AI 报告生成作为核心交付物，而不是把图表当核心。

## Q7: 项目最大的亮点是什么？

> **A**: 我认为是**"AI 不可达时仍能交付"**。我们没有把 LLM 当成系统的"心脏"，而是当成"锦上添花"。核心的数据处理、指标计算、图表生成、报告导出**全部由本地代码完成**——LLM 只做"把数字翻译成自然语言"这一件事。这意味着即使 LLM 服务挂了、限流了、超时了，用户**依然能用系统**。这一点在我们实际跑通业务流的过程中反复验证过。

## Q8: 为什么做 PDF 处理这个模块？和主功能关系是什么？

> **A**: 真实办公场景里**很多数据不是 Excel 来的**——年报是 PDF、合同是 PDF、招股书是 PDF。所以我们加了 PDF 处理模块，把 PDF 转 Word、转表格、提取文字、压缩**四个高频场景工具化**，并且都能"保存为历史任务"——这样工作台既能处理 Excel 用户，也能处理 PDF 文档用户，让系统的适用范围**扩展一个量级**。
